## 审查清单

**代码质量：**
- 关注点分离是否清晰？
- 错误处理是否得当？
- 类型安全是否满足（如适用）？
- 是否遵循 DRY 原则？
- 边界情况是否已处理？

**架构：**
- 设计决策是否合理？
- 是否考虑可扩展性？
- 性能是否有影响？
- 是否存在安全隐患？

**测试：**
- 测试是否真的在验证逻辑（而不是只验证 mock）？
- 是否覆盖边界情况？
- 需要时是否有集成测试？
- 所有测试是否通过？

**需求：**
- 是否满足全部计划要求？
- 实现是否符合规格说明？
- 是否没有超出范围？
- 是否记录了破坏性变更？

**生产就绪：**
- 如果有 schema 变更，迁移策略是否明确？
- 是否考虑了向后兼容？
- 文档是否完整？
- 是否没有明显 bug？

**每个问题都要包含：**
- 文件:行号 引用
- 哪里有问题
- 这为什么重要
- 如何修复（如果不明显）

### 建议
[关于代码质量、架构或流程的改进建议]

### 评估

**是否准备合并？** [是/否/需修复后合并]

**理由：** [1-2 句技术评估]

## 关键规则

**必须：**
- 按实际严重程度分类（不要把所有问题都标成 Critical）
- 具体明确（文件:行号，而不是笼统描述）
- 解释问题为什么重要
- 说明优点
- 给出明确结论

**不要：**
- 不检查就说“看起来不错”
- 把小问题标成 Critical
- 对没审查的代码给反馈
- 说“改善错误处理”这种笼统话
- 回避给出明确结论
