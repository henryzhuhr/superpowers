# 系统化调试

## 概述

随机修补是在浪费时间，还会制造新 bug。快速打补丁会掩盖根本问题。

**核心原则：** 在尝试修复之前，必须先找到根因。只修症状等同于失败。

**违背流程字面意思，就是违背调试精神。**

## 铁律

```
没有根因调查，就不能修复
```

如果你还没有完成阶段 1，就不能提出修复方案。

## 何时使用

用于任何技术问题：
- 测试失败
- 生产环境中的 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其是在以下情况下使用：**
- 时间压力很大时（紧急情况最容易让人去猜）
- “只是一个很快的修复”看起来很明显时
- 你已经尝试过多个修复方案时
- 上一个修复没有奏效时
- 你并不完全理解这个问题时

**不要跳过的情况：**
- 问题看起来很简单时（简单 bug 也有根因）
- 你很赶时（匆忙只会保证返工）
- 经理要求立刻修好时（系统化反而更快）

## 四个阶段

你必须完成每个阶段，才能进入下一个阶段。

### 阶段 1：根因调查

**在尝试任何修复之前：**

1. **仔细阅读错误信息**
   - 不要跳过错误或警告
   - 它们往往就包含了准确答案
   - 完整阅读堆栈跟踪
   - 记下行号、文件路径、错误码

2. **稳定复现**
   - 你能可靠地触发它吗？
   - 精确步骤是什么？
   - 每次都会发生吗？
   - 如果不能复现 → 收集更多数据，不要猜

3. **检查最近变更**
   - 什么变化可能导致了它？
   - 查看 git diff、最近提交
   - 新依赖、配置变化
   - 环境差异

4. **在多组件系统中收集证据**

   **当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

   **在提出修复前，先添加诊断埋点：**
   ```
   对每个组件边界：
     - 记录进入组件的数据
     - 记录离开组件的数据
     - 验证环境/配置是否传递
     - 检查每一层的状态

   先运行一次，收集证据，找出具体卡在哪一层
   然后分析证据，定位失败的组件
   再去调查那个具体组件
   ```

   **示例（多层系统）：**
   ```bash
   # 第 1 层：工作流
   echo "=== Secrets available in workflow: ==="
   echo "IDENTITY: ${IDENTITY:+SET}${IDENTITY:-UNSET}"

   # 第 2 层：构建脚本
   echo "=== Env vars in build script: ==="
   env | grep IDENTITY || echo "IDENTITY not in environment"

   # 第 3 层：签名脚本
   echo "=== Keychain state: ==="
   security list-keychains
   security find-identity -v

   # 第 4 层：实际签名
   codesign --sign "$IDENTITY" --verbose=4 "$APP"
   ```

   **这能揭示：** 哪一层失败了（secrets → workflow ✓，workflow → build ✗）

5. **追踪数据流**

   **当错误出现在很深的调用栈中时：**

   这个目录中的 `root-cause-tracing.md` 提供了完整的向后追踪技巧。

   **简版：**
   - 错误值最初从哪里来？
   - 是什么调用时传入了这个错误值？
   - 继续向上追踪，直到找到源头
   - 在源头修复，而不是在症状处修复

### 阶段 2：模式分析

**修复前先找到模式：**

1. **寻找可工作的示例**
   - 在同一代码库里找类似的可运行代码
   - 和坏掉的地方相比，哪里是可工作的？

2. **对照参考实现**
   - 如果是在实现某种模式，必须完整阅读参考实现
   - 不要只扫一眼，要逐行读完
   - 在应用之前，彻底理解这个模式

3. **识别差异**
   - 可工作的代码和坏掉的代码有什么不同？
   - 把每一个差异都列出来，即使很小
   - 不要假设“那个差异不重要”

4. **理解依赖**
   - 这还需要哪些其他组件？
   - 需要什么设置、配置、环境？
   - 它依赖哪些前提假设？

### 阶段 3：假设与测试

**科学方法：**

1. **提出单一假设**
   - 明确写下：“我认为 X 是根因，因为 Y”
   - 写下来
   - 要具体，不要空泛

2. **最小化测试**
   - 用最小可能的改动去验证假设
   - 一次只改一个变量
   - 不要一次修多个东西

3. **先验证，再继续**
   - 成功了吗？是 → 进入阶段 4
   - 没成功？提出新的假设
   - 不要在上面继续叠加更多修复

4. **如果你不知道**
   - 直接说“我不理解 X”
   - 不要假装懂了
   - 请求帮助
   - 继续研究

### 阶段 4：实现

**修复根因，而不是症状：**

1. **创建失败测试用例**
   - 尽可能简单的复现
   - 如果可以，写自动化测试
   - 如果没有框架，就写一次性的测试脚本
   - 修复之前必须先有
   - 编写合适的失败测试时，使用 `superpowers:test-driven-development` skill

2. **实施单一修复**
   - 只处理已经识别出的根因
   - 一次只改一处
   - 不要顺手优化别的东西
   - 不要把重构和修复打包在一起

3. **验证修复**
   - 现在测试通过了吗？
   - 其他测试没有坏吗？
   - 问题真的解决了吗？

4. **如果修复没成功**
   - 停止
   - 统计：你已经尝试了多少个修复？
   - 如果少于 3 个：回到阶段 1，用新信息重新分析
   - **如果大于等于 3 个：停止并质疑架构（见第 5 步）**
   - 不要在没有架构讨论的情况下尝试第 4 个修复

5. **如果 3 次以上修复都失败了：质疑架构**

   **表明可能是架构问题的模式：**
   - 每次修复都在不同位置暴露新的共享状态/耦合/问题
   - 修复需要“巨大重构”才能落地
   - 每次修复都会在别处制造新症状

   **停止并质疑基本前提：**
   - 这种模式本质上是否合理？
   - 我们是不是只是在“靠惯性坚持”？
   - 应该重构架构，还是继续修补症状？

   **在尝试更多修复之前，先和你的 human partner 讨论**

   这不是失败的假设，而是错误的架构。

## 红旗 - 立即停止并遵循流程

如果你发现自己在想：
- “先快速修一下，调查以后再说”
- “先随便改 X，看看会不会好”
- “加多个改动，一起跑测试”
- “测试先别写，我手动验证就行”
- “大概率就是 X，我直接修这个”
- “我没完全理解，但这个可能管用”
- “模式是 X，但我想换种方式适配”
- “这里列出主要问题：[没调查就直接列修复项]”
- 在追踪数据流之前就开始提方案
- **“再试一个修复就好”（在已经试了 2 次以上时）**
- **每次修复都暴露出别处的新问题**

**这些全都意味着：停止。回到阶段 1。**

**如果 3 次以上修复失败：质疑架构（见阶段 4.5）**

## 你的 human partner 发出的“你做错了”的信号

**留意这些纠偏：**
- “那真的发生了吗？” - 你在没验证的情况下做了假设
- “它会显示出……吗？” - 你本该先增加证据收集
- “别猜了” - 你在没理解问题前就提出修复
- “深入想想这个” - 要质疑基本前提，而不只是症状
