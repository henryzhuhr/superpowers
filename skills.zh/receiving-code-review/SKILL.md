# 接收代码审查

## 概述

代码审查需要技术评估，而不是情绪表演。

**核心原则：** 先验证，再实现。先提问，再假设。技术正确性高于社交舒适度。

## 响应模式

```
收到代码审查反馈时：

1. 阅读：完整读完反馈，不要立刻反应
2. 理解：用自己的话复述需求（或提问确认）
3. 验证：对照代码库中的真实情况检查
4. 评估：对这个代码库而言，技术上是否成立？
5. 回复：给出技术性的认可，或者基于理由的反驳
6. 实施：一次只做一项，并逐项测试
```

## 禁止的回复

**绝对不要：**
- "You're absolutely right!"（明确违反 CLAUDE.md）
- "Great point!" / "Excellent feedback!"（表演式）
- "Let me implement that now"（在验证之前）

**应该这样做：**
- 复述技术需求
- 提出澄清问题
- 如果建议不对，用技术理由反驳
- 直接开始工作（行动优先于言语）

## 处理不清楚的反馈

```
如果任何条目不清楚：
  先停下 - 暂时不要实现任何东西
  针对不清楚的条目先请求澄清

原因：条目之间可能相关。只理解一部分 = 错误实现。
```

**示例：**
```
你的协作伙伴： "Fix 1-6"
你理解了 1、2、3、6，但 4、5 不清楚。

❌ 错误：先实现 1、2、3、6，之后再问 4、5
✅ 正确： "我理解 1、2、3、6。第 4 和第 5 项在继续前需要澄清。"
```

## 来源相关处理

### 来自你的协作伙伴
- **可信** - 理解之后就实现
- **但仍要问** 如果范围不清楚
- **不要表演式认可**
- **直接行动** 或给出技术性回应

### 来自外部审查者
```
在实现之前：
  1. 检查：对这个代码库来说技术上正确吗？
  2. 检查：会破坏现有功能吗？
  3. 检查：当前实现是否有原因？
  4. 检查：在所有平台/版本上都能工作吗？
  5. 检查：审查者是否理解完整上下文？

如果建议看起来不对：
  用技术理由反驳

如果无法轻易验证：
  直接说明："如果没有 [X]，我无法验证这一点。要我 [调查/询问/继续] 吗？"

如果与协作伙伴之前的决定冲突：
  先停下，和你的协作伙伴讨论
```

**你的协作伙伴的规则：** "外部反馈要保持怀疑，但要仔细核查。"

## 对“专业化”功能做 YAGNI 检查

```
如果审查者建议“正确地实现”：
  用 grep 在代码库中搜索真实使用情况

  如果未使用："这个端点根本没被调用。按 YAGNI 处理，删掉？"
  如果已使用：那就正确地实现
```

**你的协作伙伴的规则：** "你和审查者都向我汇报。如果不需要这个功能，就不要加。"

## 实施顺序

```
对于多项反馈：
  1. 先澄清所有不清楚的内容
  2. 然后按这个顺序实现：
     - 阻塞性问题（破坏、安全）
     - 简单修复（拼写、导入）
     - 复杂修复（重构、逻辑）
  3. 每修一项就单独测试
  4. 验证没有回归
```

## 何时反驳

在以下情况反驳：
- 建议会破坏现有功能
- 审查者缺少完整上下文
- 违反 YAGNI（未使用的功能）
- 对这个技术栈来说技术上不正确
- 出于旧版/兼容性原因需要保留
- 与协作伙伴的架构决策冲突

**反驳方式：**
- 用技术理由，而不是防御情绪
- 提出具体问题
- 引用已工作的测试/代码
- 架构相关时，让你的协作伙伴介入

**如果你不方便直接反驳，可以用这句信号：** "情况有些不对劲。"

## 认可正确反馈

当反馈是正确的：
```
✅ "已修复。[简要说明改了什么]"
✅ "好发现 - [具体问题]。已在 [位置] 修复。"
✅ 直接修复并在代码里体现

❌ "You're absolutely right!"
❌ "Great point!"
❌ "Thanks for catching that!"
❌ "Thanks for [任何内容]"
❌ 任何感谢表达
```

**为什么不说谢谢：** 行动胜于语言。直接修复即可。代码本身会表明你接收到了反馈。

**如果你发现自己正要写 "Thanks"：** 删掉。只说明修复。

## 优雅地纠正你的反驳

如果你先前反驳但后来发现自己错了：
```
✅ "你说得对 - 我检查了 [X]，它确实会 [Y]。现在开始实现。"
✅ "我已经验证过了，你是对的。我的初始理解错了，因为 [原因]。正在修复。"

❌ 冗长道歉
❌ 为之前的反驳辩护
❌ 过度解释
```

只要客观陈述纠正结果，然后继续。

## 常见错误

| 错误 | 修正 |
|---------|-----|
| 表演式认可 | 直接说明需求或直接行动 |
| 盲目实现 | 先对照代码库验证 |
| 批量改动却不测试 | 一次一项，逐项测试 |
| 假设审查者一定正确 | 检查是否会破坏现有行为 |
| 回避反驳 | 技术正确性 > 舒适度 |
| 只实现一部分 | 先澄清所有不清楚项 |
| 无法验证还继续做 | 说明限制并请求指示 |

## 真实示例

**表演式认可（错误）：**
```
审查者："Remove legacy code"
❌ "You're absolutely right! Let me remove that..."
```

**技术验证（正确）：**
```
审查者："Remove legacy code"
✅ "我检查过了……构建目标是 10.15+，而这个 API 需要 13+。这里为了向后兼容需要保留旧实现。当前实现的 bundle ID 也不对 - 是修正它，还是直接放弃 13 之前的支持？"
```

**YAGNI（正确）：**
```
审查者："Implement proper metrics tracking with database, date filters, CSV export"
✅ "我搜过代码库了，没有任何地方调用这个端点。要按 YAGNI 直接删掉吗？还是我漏看了某些使用场景？"
```

**不清楚的条目（正确）：**
```
你的协作伙伴："Fix items 1-6"
你理解了 1、2、3、6，但 4、5 不清楚。
✅ "我理解 1、2、3、6。在实现前，需要先澄清第 4 和第 5 项。"
```

## GitHub 线程回复

回复 GitHub 上的行内审查评论时，要在线程里回复（`gh api repos/{owner}/{repo}/pulls/{pr}/comments/{id}/replies`），不要作为 PR 顶层评论。

## 最终结论

**外部反馈 = 需要评估的建议，不是必须照做的命令。**

先验证。再质疑。然后再实现。

不要表演式认可。技术严谨始终优先。
